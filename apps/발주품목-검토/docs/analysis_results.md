# 발주품목검토 프로그램 종합 리뷰 및 개선안

## 1. 프로그램 로직 쉬운 설명 (전체 흐름)

이 프로그램은 각 팩토리(공장)에서 올라오는 **자재 요청 데이터**를 확인하고, **재고 상황과 단가, 과거 소모량 데이터**를 취합하여 **"오늘 당장 어디에 얼마만큼의 자재를 발주해야 하는가?"**를 자동으로 계산해주는 일종의 **"디지털 자재 통제탑"**입니다.

### 📦 핵심 데이터 수집 (어디서 무엇을 보는가?)
- **자재요청 시트**: 각 팩토리에서 급하게 필요한 자재들의 명단(미불출 건)
- **장현석_재고현황 & 재고소진예상시점**: 현재 중앙 창고에 남은 재고량과, 과거 8주간 하루에 몇 개씩 썼는지, 그리고 이번 달에는 하루에 몇 개씩 쓸 것 같은지(AI 예측)
- **발주관리_단가테이블**: 각 자재를 누구에게 사야 하는지(공급업체), 최소 몇 개부터 살 수 있는지(MOQ), 박스당 몇 개가 들어있는지(단위), 배송엔 며칠 걸리는지(리드타임)
- **발주관리_PO List**: 이미 과거에 주문해서 오고 있는 중인 자재들(미입고 재고)

### 🚚 발주 판단 로직 (어떻게 결정하는가?)
프로그램은 자재를 크게 두 가지 성격으로 나누어 처리합니다. (마치 **택배 직배송**과 **본사 창고 비축**의 차이입니다.)

**A. 직납 품목 (팩토리로 바로 쏘는 자재)**
- 창고 재고를 따지지 않습니다. 팩토리가 달라고 한 수량을 **100% 그대로 발주**합니다.
- 단, 도매상(공급업체)이 "우리는 무조건 박스 단위로만 팔아요" 또는 "최소 100개 이상만 팔아요(MOQ)"라고 하면, 거기에 맞춰서 수량을 **올림 처리**합니다.
- 성수/군포로 가는 건 '진주크린텍'에, 부산으로 가는 건 '경동라인'에 알아서 배정(라우팅)합니다.

**B. 일반 품목 (본사 창고에 쟁여두는 자재)**
- 팩토리에서 달라고 했다고 무작정 사지 않습니다.
- **예상 소모량 공식**: `(하루 평균 소모량) × (배송 걸리는 날짜) × (안전재고 비율)`
- 현재 재고와 이미 오고 있는 재고(미납 PO)를 합친 수량이 **예상 소모량보다 적을 때만** 부족한 만큼 창고용으로 발주합니다.
- 대량으로 막 쓰는 자재면 파렛트(Pallet) 단위로 크게 사고, 적게 쓰는 거면 박스 단위로 구매합니다.

## 2. 🚨 치명적 오류 진단 (결과값이 예상과 달랐던 이유)

코드를 딥다이브한 결과, **데이터가 예상과 다르게 나오는 치명적인 논리적 결함(Bug)**을 발견했습니다.

> [!CAUTION]
> **일반 품목 발주 시, 팩토리의 '요청 수량'이 완전히 무시되고 있습니다.**

* `src/core/procurementLogic.js`의 88번째 줄 이후(일반 품목 로직)를 보면, `requestedQty`(팩토리가 이번에 달라고 요청한 총량) 변수가 계산에 단 한 번도 쓰이지 않고 버려집니다.
* **증상**: 팩토리에서 갑자기 특정 일반 자재를 1만 개 달라고 요청(자재요청 시트에 등록)하더라도, 프로그램은 이를 인지하지 못합니다. 오직 "평소 하루에 쓰던 양"과 "현재 창고 재고"만 비교하여 발주 수량을 0으로 계산해버리는 현상이 발생합니다.
* **해결 방안**: 가용 재고(`availableStock`)를 계산할 때, 현재 재고와 미입고 PO를 더한 값에서 **이번에 팩토리가 요청한 수량(`requestedQty`)을 반드시 빼주거나**, 필요 소요량에 더해주는 로직이 즉시 추가되어야 합니다.

**기타 잠재적 문제점:**
- **주말 배송 지연 계산 오류**: 리드타임이 긴 자재의 경우 배송 기간 중간에 끼어있는 주말은 계산하지 않고, 오직 '도착 예정일'이 토/일요일일 때만 월요일로 미루는 단순한 로직이 적용되어 있어 실제보다 리드타임이 짧게 계산될 수 있습니다.

## 3. Rule A-1 앱 표준 규격 기반 구조 리뷰

현재 폴더(`ai/laundrygo/apps/발주품목검토`)의 구조를 AI Agent 표준 룰(Rule A-1)에 비추어 보았을 때, 몇 가지 개선이 시급한 상태입니다.

> [!WARNING]
> **Rule A-1 (루트 청정 구역 유지 및 데이터 로테이션) 위반 사항**

1. **루트 폴더 오염**: 규정상 루트에는 메인 실행 파일 1~2개만 있어야 하나, `scratch_headers.js`, `test_logic.js`, `check_duplicates.js` 등 수많은 테스트 파일과 찌꺼기가 혼재되어 있어 유지보수에 큰 혼란을 줍니다. (반드시 `scripts/`나 `archive/`로 격리 필요)
2. **데이터 로테이션 부재**: `output/` 폴더에 엑셀 파일이 계속 쌓이기만 하고, `archive/YYYY-MM-DD(요일)` 형태로 과거 데이터를 압축/이동하는 로직이 빠져 있습니다.
3. **사용 언어 편차**: 해당 시스템은 JavaScript(Node.js)로 짜여 있습니다. 현재 우리 AI Agent의 모든 하네스 룰과 자동화 모듈은 Python을 표준으로 상정하고 있으므로, 장기적인 확장성과 에이전트의 자체 유지보수를 고려할 때 Python 베이스로의 전환이 이상적입니다.

## 4. 향후 진행 방향성 제안 (검토 요망)

문제 원인과 구조적 비효율성이 명확해졌습니다. 이제 코드를 수정해야 하는데, 아래 3가지 옵션 중 어떤 방향으로 진행하는 것이 재욱님의 향후 관리에 가장 유리할지 검토해 보시기 바랍니다.

- **Option A (최소 수정 - Quick Fix)**: 현재 JS 코드 상태를 그대로 유지하되, 위에서 발견한 치명적 버그(요청 수량 누락)와 일부 오작동만 고쳐서 당장의 발주 결과만 정상화합니다.
- **Option B (JS 유지 + 구조 리팩토링)**: 언어는 Node.js로 유지하되, 버그를 고치면서 Rule A-1에 맞게 루트 폴더의 찌꺼기 파일들을 싹 청소하고, 데이터 로테이션(archive 이동) 로직을 추가하여 시스템을 깔끔하게 만듭니다.
- **Option C (Python 전면 재작성 - 권장)**: 현재 로직을 Python(`.py`) 기반으로 100% 새로 짭니다. 이 경우 우리의 AI 하네스 룰(Rule A-1)을 완벽히 준수하는 최적화된 앱 구조가 탄생하며, 앞으로 제가 다른 파이썬 자동화 스크립트들과 연동하거나 수정하기가 훨씬 쉬워집니다.

현재 상황과 필요에 맞는 방향을 편하게 선택해 주시거나, 궁금한 점을 말씀해 주시면 즉각 반영하겠습니다.
